---
name: Tap to Pay Apple review contract
description: Non-obvious constraints from Apple's Tap to Pay on iPhone UX checklist (v1.8) that the mobile PoS implementation depends on.
---

Apple's publishing entitlement review (checklist v1.8, attached*assets/Getting_Started_App_Requirements_and_Review*\*.pdf) imposes contracts that aren't obvious from the Stripe SDK:

- Never persist "Tap to Pay enabled" locally (Req 1.6) — T&C acceptance state belongs to Apple/the PSP. Only the awareness-moment-shown flag is stored (per seller pubkey).
- Enablement = the first `connectReader({ discoveryMethod: "tapToPay", tosAcceptancePermitted: true })`; the Stripe SDK presents Apple's Terms & Conditions natively. There is no separate T&C API. Any enable path (awareness modal, Settings, checkout) funnels through `enableTapToPay` in apps/mobile/lib/pos-tap-to-pay.ts.
- Warmup (Req 1.5/5.6) = a throwaway tapToPay `discoverReaders` + `cancelDiscovering`; single-flight module-wide, and checkout must `awaitPendingTapToPayWarmup()` before discovering or the two discoveries collide and error.
- The beta.34 RN `StripeTerminalProvider` NEVER auto-initializes: mounting it only exposes `initialize()` via context, and every hook method throws until a child calls it. `TapToPayProvider` (components/tap-to-pay-provider.tsx) renders an initializer child for this; anything firing early must also poll `getIsInitialized()`.
- The native SDK keeps the Tap to Pay connection alive across provider mounts. Enable paths and checkout must check `getConnectedReader()` first and reuse the live connection — a fresh discovery against a connected reader errors.
- Checkout payment list: Tap to Pay first, never disabled/hidden for eligible sellers (5.2/5.3); eligibility = module shipped + Stripe chargesEnabled + `supportsReadersOfType` device probe.
- Merchant education (Req 4.1): Apple's Nov 2026 entitlement review OVERTURNED the custom-screens-only decision — the current App & Marketing Requirements and Review Guide marks 4.1 (ProximityReaderDiscovery, iOS 18+) Required and says it can be integrated directly when the PSP SDK doesn't expose it (Stripe Terminal RN beta.34 doesn't). A local Expo module at modules/proximity-reader-discovery presents Apple's own sheet (.howToTap content), which Apple counts as fulfilling 4.4/4.6/4.7/4.8. presentAppleTapToPayEducation() in lib/tap-to-pay-education.ts is the single entry point: it returns false on Android, iOS <18, web, missing module, or any presentation error, and every caller MUST then show the custom slides (Marketing Guide/Toolkit copy, never self-made iPhone imagery) so education can never silently vanish. Wired at all three touchpoints: awareness + Settings enable (post-T&C), Settings "Review the education" (re-presents Apple's sheet), and the first-charge gate in pos/card.tsx where the native await doubles as the dismissal gate. Seen flag stays keyed per-pubkey in AsyncStorage.

- On device, "First initialize the Stripe Terminal SDK before performing any action" usually means the tokenProvider fetch failed, not an SDK bug: beta.34's initialize awaits tokenProvider() before native init, so a 404/403 on /api/stripe/terminal/connection-token leaves the SDK permanently uninitialized and EVERY later action throws that misleading error. First check: `curl -X POST https://self-sown.com/api/stripe/terminal/connection-token` — 404 = deployed app predates the Terminal endpoints (publish fixes it), 401/403 = auth or Connect-account state. Device logs do NOT stream to Metro over a cloudflared tunnel, so diagnose from the server side.
- That raw init error must NEVER reach sellers: every Tap to Pay enable/charge failure funnels through describeTapToPayEnableFailure (pos-tap-to-pay.ts), which maps stripe_not_connected (PosApiError.code from posPost) and the swallowed-403 init error — re-checked via fetchPosPaymentMethods — to "Connect a Stripe account with card charges to use Tap to Pay." Any new enable/charge surface must use it too; non-throw paths (SDK result.error strings) test with isSdkNotInitializedError.
- The provider skips initialize() entirely when payment methods show card charges disabled — otherwise the doomed init's console.error pops a dev-build LogBox on mere navigation to a Tap to Pay screen. Init polls (warmup, awareness) treat a throwing getIsInitialized as "not yet" rather than rejecting unhandled.
- After Stripe connect, the SDK must auto-init without a screen remount: the connect browser sheet never backgrounds the app on iOS, so AppState alone can't catch it. The dashboard connect flow fires requestTerminalSdkInit() (lib/terminal-init-signal.ts pub/sub) on return; the provider's initializer subscribes and re-attempts (also on AppState "active"). New connect entry points must fire the same signal.
- The SDK context recreates its callbacks (incl. initialize) whenever provider state flips — init itself toggles `loading`, so an effect depending on those callbacks re-fires per render, and a failing init loops into an endless console.error LogBox storm with no user action. Pin such effects to refs + [session] deps, and keep every StripeTerminalProvider prop (localeConfig!) a hoisted constant, not an inline object.
- initialize() console.errors inside the SDK when its tokenProvider throws (no catch of ours can intercept), and every guarded hook method console.errors "First initialize..." before throwing — each one a dev-build LogBox popup. So preflight createStripeTerminalConnectionToken before initialize() and skip on refusal; describeTapToPayEnableFailure probes the same endpoint so a deterministic refusal (e.g. 422 missing business address) surfaces its actionable server message instead of "still starting up".

- Unblocking a seller whose account lacks an address: the platform CANNOT write business_type/company/individual on OAuth Express accounts (Stripe 403 oauth_not_supported), but it CAN create the Terminal location directly on the connected account (terminal.locations.create with stripeAccount) — and once any location exists, ensureTerminalLocation short-circuits on it forever (address never needed again). Stripe also fast-paths repeat onboarding with the same email/phone, so a new account can come back with charges enabled but NO address; the address the seller typed may have landed on the PREVIOUS account.

- Tap to Pay copy/artwork/marks/disclaimers are platform-conditional across EVERY seller-facing surface (awareness, education, Settings screen + settings list entry, cart payment button, card checkout, unsupported-device message): iOS keeps the Apple-review wording byte-identical; Android gets device-neutral copy, no Apple artwork/marks, no Apple disclaimer. Any new Tap to Pay copy surface must branch on Platform.OS — a surface added iOS-only leaks iPhone wording to Android sellers.

**Why:** the app must pass Apple's UX review to get the publishing entitlement (required even for TestFlight).
**How to apply:** when touching PoS card checkout, the awareness modal, or Settings tap-to-pay, keep these invariants; re-check the checklist PDF for new requirements when it revs.
