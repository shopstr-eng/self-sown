---
name: Next build OOM contention
description: Cold Turbopack build OOMs were caused by Tailwind v4 auto source detection scanning the multi-GB .local/.cache dirs (~4.4GB of the ~6.5GB peak); fixed via source(none) + explicit @source globs in globals.css — cold build now ~2.1-2.4GB. The dev-server.sh supervisor owns builds as a host-noise safety net.
---

Cold `next build` (Turbopack, Next 16.3.4) used to peak ~6.5-7GB and coin-flip SIGKILL (exit 137, or a misleading PostCSS "unexpected end of file" panic). Bisected 2026-09: the app JS graph is NOT the problem — a trivial 1-page app with the real `_app.tsx` still peaked ~5.9GB, and excluding all 203 API routes moved the peak <3%. The dominant contributor was the `globals.css` compile: bare `@import "tailwindcss"` alone cost ~4.4GB because Tailwind v4 automatic source detection walked the whole workspace, including the multi-GB `.local/` and `.cache/` dirs (not covered by .gitignore-driven ignores), turning junk text into false-positive utility candidates — which also bloated the shipped CSS by ~107KB of garbage rules. Fix: `@import "tailwindcss" source(none)` + explicit `@source` globs mirroring tailwind.config content globs. Result: cold build ~2.1-2.4GB peak, ~40s wall (was ~6.5GB, ~4min).

**Why:** Turbopack build memory here is native (V8 heap stayed ~64MB — heap caps are nearly irrelevant) and scales with what gets parsed/scanned, not with route count. Neither `bundlePagesRouterDependencies` (Turbopack ignores it for pages builds), `optimizePackageImports` (@heroui barrel), nor `turbopackPluginRuntimeStrategy` (workerThreads vs childProcesses — the PostCSS child balloons either way) moved the peak. The VM's `free` shows ~2GB used outside our cgroup (host noise we cannot free), so even a slimmed build can SIGKILL when something else heavy (typecheck, tsserver ~1.5-2.5GB, tests) runs concurrently. `experimental.turbopackFileSystemCacheForBuild: false` (dev-only MM_DEV_BUILD gate in next.config.mjs) also helps — the 16.3.x default-on FS build cache buffers serialization in memory. If cold builds start SIGKILLing again after a Next minor bump, check the config schema for newly-defaulted memory features before tuning heap.

**Why a supervisor:** even with the levers above, host memory noise still kills some cold builds, and the workflow's 300s port wait kills slow ones. The `dev` script is `bash scripts/dev-server.sh` (see its header for the current behavior contract: port-first status page, memory gate at 3000MB, IDE kill, OOM retries, last-good fallback, self-heal loop). A placeholder page at the preview = a build is in flight or self-healing — read the workflow log before concluding anything is broken, and don't hand-run cold `next build` alongside it.

**How to apply:** never verify web-build health with a bare `pnpm run build` — it OOMs (exit 137) even with GBs free because it lacks the supervisor's `RAYON_NUM_THREADS=2` cap and memory gate. Restart the "Next.js Dev Server" workflow and read its log for `build exited 0`; a `.next-dev-status` of `broken` means a real compile error (exit 1), `failed` means repeated OOM. If build memory regresses, measure first with scripts/measure-build-peak.sh (RSS sampler + --experimental-debug-memory-usage; process is named `next-build`, not `next build`) and bisect with `--debug-build-paths`. When editing tailwind.config.ts `content` globs, mirror the change into the `@source` lines in styles/globals.css. Verify CSS parity by selector-diffing `.next/static/chunks/*.css` against a known-good build, not byte size. Behavior changes to the supervisor must keep scripts/dev-server.test.sh green (stub-based, no real build). Traps it guards: bash `if cmd; then` without `else` resets `$?` to 0 (capture failures in an explicit `else`), and a background retry loop must re-classify each failure or a real compile error gets retried forever behind an "OOM retrying" status page.
